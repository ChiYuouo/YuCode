# MewCode Agent Loop Spec

## 背景

MewCode 已具备多模型流式对话和六项核心工具，但单次请求最多只执行一个工具，工具结果回传后不能继续自主行动。用户必须反复催促，才能完成需要多步观察、操作和修正的任务。本章引入 Agent Loop，使 MewCode 能在安全边界内持续调用模型和工具，直到任务完成或触发明确停止条件。

## 目标

- 让普通请求与 `/do` 请求可自主完成多轮“模型判断 → 工具执行 → 结果回传”。
- 让 `/plan` 请求只使用只读能力探索上下文并输出计划，不产生副作用。
- 通过统一异步事件流解耦 Agent 与界面，同时保留实时流式文本。
- 安全高效地执行一轮中的多个工具调用，并维持模型给出的依赖顺序。
- 对正常完成、迭代上限、取消、重复未知工具和流错误提供明确且可观察的结束状态。

## 功能需求

- F1：普通请求和带内容的 `/do` 请求进入完整 Agent Loop。每轮模型响应若包含工具调用，系统执行后将结果回传模型并继续下一轮；模型不再请求工具时正常结束。
- F2：每次模型调用计为一次迭代。默认最多 10 次，可由项目配置覆盖为有效正整数；达到上限后不再调用模型或工具，并明确告知用户。
- F3：用户取消时立即停止安排后续迭代，并尽快中断正在进行的模型请求或命令；短暂且无法安全中断的文件操作结束后不得继续循环。
- F4：模型请求未知工具时，将结构化失败结果回传供其纠正。连续两轮仍请求未知工具则停止；任一有效工具得到执行后连续计数清零。同一轮包含多个未知调用只记作一轮。
- F5：任一模型流在开始、进行或收尾阶段出错时，本轮立即停止，保留已经展示的文本与已完成的工具结果，并向界面发送明确错误和停止原因。
- F6：Agent 对外产生有序的异步事件流，至少包含文本增量、工具调用、工具结果、Token 用量和进度；界面只消费事件，不负责驱动循环或决定工具调度。
- F7：流式收集同时完成两件事：文本增量到达后立即向界面发出，并在内部累积完整响应；不得因等待完整响应而延迟界面显示。
- F8：一次模型响应可包含多个工具调用。系统保持原始顺序，将相邻只读调用组成并发批次；写文件、改文件和执行命令分别串行执行，并作为前后批次的顺序屏障。
- F9：同一批次全部结束后，所有工具结果按原调用顺序一次性回传模型；单个工具失败作为结果进入下一轮，不导致 Agent 崩溃或跳过其他已安排调用。
- F10：`/plan` 进入只读规划流程，仅向模型开放读取文件、查找文件和搜索代码能力，可多轮探索，最终输出计划；不得写文件、改文件或执行命令。
- F11：`/do` 不自动引用最近一次 `/plan` 的内容，用户必须在命令后附上要执行的内容；普通消息与 `/do` 均开放完整工具集。
- F12：保留现有命令执行确认机制。它只适用于命令工具；本章不新增针对写文件或改文件的交互式确认。
- F13：Agent 在每轮开始、工具批次执行和最终停止时提供进度信息，使界面可以展示当前迭代、正在进行的阶段及结束原因。
- F14：整个 Agent 运行期间累计各轮 Token 用量，并通过事件让界面持续更新；最终结果包含本次请求的合计用量。

## 非功能需求

- N1：OpenAI 与 Claude 后端使用相同的 Agent 行为、事件语义、停止条件和工具调度规则。
- N2：事件必须按单次请求的因果顺序输出；即使工具并发完成，向模型回传和向界面呈现时也保持原调用顺序。
- N3：Agent 的循环、工具等待和事件消费不得阻塞界面响应；流式文本到达后应及时可见。
- N4：取消、工具失败、模型流错误和触顶停止后，会话历史必须保持可继续对话的有效状态，不写入伪造的成功结果。
- N5：沿用现有工作目录边界、工具超时、输出截断和命令确认规则，不降低上一章已有安全限制。
- N6：异常配置应在启动阶段给出清晰错误，不允许以无上限或非正数方式运行 Agent。
- N7：新增能力不得破坏既有纯文本对话、thinking 展示、多轮历史和 Token 总量展示。

## 不做的事

- 不实现通用权限系统、操作系统级沙箱或按工具配置权限。
- 不实现写入、修改等操作前的新增交互式确认；现有命令确认继续保留。
- 不实现上下文压缩、摘要、裁剪或超长会话管理。
- 不实现 Agent 主动向用户追问并暂停等待回答的交互式工具。
- 不分析多个工具调用之间的隐式依赖；仅以调用顺序和副作用屏障保证执行次序。
- 不持久化 `/plan` 结果，也不让 `/do` 自动查找或复用历史计划。
- 不实现跨请求继续未完成 Agent、后台运行或任务恢复。

## 验收标准

- AC1（F1）：模型依次请求多个工具轮次时，MewCode 自动执行、回传结果并继续，无需用户再次催促；当模型返回纯文本且无工具调用时正常结束。
- AC2（F2）：默认配置下第 10 次模型调用仍要求继续时，系统不发起第 11 次调用，界面显示达到迭代上限；配置为其他正整数时按新上限生效，无效值导致清晰的启动错误。
- AC3（F3）：在模型流式生成和命令执行期间分别触发取消，二者都尽快停止，之后没有新模型调用或工具调用，输入恢复可用。
- AC4（F4）：首次请求未知工具后，模型收到结构化失败结果并可纠正；连续第二轮仍请求未知工具时停止。中间成功执行有效工具后，再次未知按首次重新计数。
- AC5（F5）：模拟模型流在首段前、文本输出中和结束阶段报错时，Agent 均停止并发出错误原因；已显示文本和已完成工具结果仍保留，会话可继续。
- AC6（F6、F13）：一次包含工具的请求能依次观察到文本、工具调用、工具结果、用量和进度事件；进度可辨认迭代序号、运行阶段和最终停止原因，界面无需直接调用循环控制逻辑。
- AC7（F7）：模型分多段输出文本时，每段到达后立即出现在界面；该轮结束后，后续判断和历史中使用的文本与所有分段拼接结果一致。
- AC8（F8）：同一响应按“读 A、读 B、写 C、读 D、命令 E”的顺序请求工具时，A/B 可重叠执行，C、D、E 依次跨屏障执行；没有调用被重排到屏障另一侧。
- AC9（F9）：并发只读调用以不同顺序完成时，工具结果仍按模型原调用顺序回传；其中一项失败不妨碍同批其他调用完成，失败结果进入下一轮。
- AC10（F10）：`/plan` 可连续调用读取、查找和搜索工具后输出计划；模型看不到写入、修改和命令工具，执行期间工作目录内容不发生变化。
- AC11（F11）：普通消息和带内容的 `/do` 都可调用完整工具集；`/do` 不带执行内容时不启动 Agent，并显示用法提示；它不会自动执行之前 `/plan` 的输出。
- AC12（F12）：完整模式请求命令时仍出现现有确认界面；拒绝后命令不执行且结果回传，文件写入与修改不新增确认步骤。
- AC13（F14）：多轮模型调用分别产生用量时，界面持续收到更新，最终显示的本次请求合计等于各轮用量之和。
- AC14（全部）：OpenAI 与 Claude 分别完成一次“读取项目信息 → 修改文件 → 验证结果 → 最终回复”的真实端到端请求，过程中无需额外催促，停止原因和最终结果正确。

# TUI 活动动效补充 Spec

## 背景

当前界面以静态文字提示模型思考、请求模型和执行工具。用户难以一眼分辨界面是在等待、思考，还是已经停止；同时应避免为了状态反馈而让已完成内容持续变化。

## 目标

- 为所有正在进行的 Agent 阶段提供统一、轻量且可见的动态状态反馈。
- 保持正式回答、已完成思考记录和已完成工具结果静态、易于阅读。
- 让动效与现有流式输出、取消和模式切换共存，不改变 Agent 的执行语义。

## 功能需求

- F15：模型等待、模型思考与工具执行期间，界面显示统一风格的循环活动标记及当前阶段文字；当前阶段结束后，活动标记立即停止并从该阶段显示中移除。
- F16：工具开始执行时显示其名称和进行中状态；工具完成后用现有成功或失败结果替换进行中状态，不保留动态标记。
- F17：思考内容仍默认折叠在正式回答上方；思考进行中时其折叠标题带活动标记，正式回答开始、工具阶段开始或请求结束时标题变为静态状态。
- F18：用户取消、模型流错误、迭代上限或正常完成时，所有活动标记停止，输入恢复后界面不得继续刷新动效。

## 非功能需求

- N8：动效刷新频率应适合终端环境，不造成可感知的输入卡顿或持续高 CPU 占用。
- N9：动效只表达当前活动状态，不改变流式文本、工具结果、Token 用量、滚动规则或会话历史。
- N10：终端不支持颜色或动画时，状态文字仍能清晰表达当前阶段。

## 不做的事

- 不加入装饰性背景、粒子、进度百分比或与 Agent 状态无关的常驻动画。
- 不改变模型思考内容的可见性策略，也不新增需求澄清流程。
- 不为每个模型或工具定制不同动效主题。

## 验收标准

- AC15（F15）：发起模型请求、收到思考、执行工具时，分别可观察到活动标记和正确阶段文字；阶段结束后该标记停止。
- AC16（F16）：模型请求工具后，完成结果出现前可观察到对应工具的进行中状态；成功和失败时均被静态结果替换。
- AC17（F17）：思考期间的折叠标题带活动标记，思考结束后保持折叠且显示静态标题，正式回答仍位于其下方。
- AC18（F18）：正常完成、取消、流错误和触顶后，等待一个刷新周期，界面不再更新活动标记，输入可用。
- AC19（N8～N10）：长时间模型等待和工具执行时，输入取消仍立即响应；在普通终端中状态文字可读，流式回答和工具结果顺序不变。
