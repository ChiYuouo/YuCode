# Agent Team 与 Coordinator Mode Spec

## 背景

YuCode 已提供子 Agent、后台任务和 Git Worktree 隔离，但多个 Agent 仍主要由主 Agent 临时发起和汇总，缺少可长期保存的团队身份、成员间直接协作、统一任务依赖和可恢复的成员上下文。对于需要并行实施和审查的复杂目标，主 Agent 应能成为 Team Lead，创建可持续协作的 Agent Team，并在必要时只承担编排与决策职责。

## 目标

- 让 Lead 能创建、管理和删除可持久化的 Agent Team，派生并复用多个队员。
- 让队员通过共享任务和点对点邮箱协作，减少所有信息经由 Lead 转发的需要。
- 为可写队员默认提供彼此隔离的 Git Worktree，并在工作完成后由 Lead 安全收敛变更。
- 提供三种本地执行方式，并按环境能力自动选择且透明报告选择结果。
- 通过双锁启用 Coordinator Mode，使 Lead 专注于拆解、派工、沟通、合并与决策。

## 功能需求

### F1：长期团队与成员花名册

Lead 可创建具名团队，并持久化团队负责人、成员花名册、团队状态和专用数据位置。团队名称必须采用用户明确给出的名称，不得因任务内容自行改名。每名成员至少具有稳定名称、角色、工作目录、执行后端、是否需要计划审批和可恢复状态。

成员未明确声明写权限时默认只读，并使用主工作目录，不创建 Git Worktree。对于读取、搜索、解释、审查或总结类任务，Lead 应登记只读成员；只有任务明确需要修改项目文件时，Lead 才登记可写成员，并为其创建独立 Git Worktree。团队数据按团队名称隔离存放于当前项目中以 YuCode 品牌命名的本地状态目录，禁止继续使用或生成旧 MewCode 品牌目录；重启 YuCode 后可被重新发现和继续使用。

### F2：三种成员执行后端与环境选择

系统支持在 tmux pane、iTerm2 pane 和当前进程内运行成员。前两种后端应运行完整且相互隔离的成员实例；进程内后端适用于轻量协作。创建成员时，系统按环境能力与既定优先级选择可用后端，并向 Lead 显示实际选择和原因；用户明确指定不可用后端时必须失败并说明原因，不得改用其他后端。自动选择没有合格后端时也必须明确失败，不得静默降级。

### F3：成员专用协作工具与审批

团队成员可使用共享任务能力，创建、查询、更新和完成带依赖关系的任务；任务状态变化后，依赖已全部满足的后续任务应自动变为可执行。团队成员还可向其他已登记成员发送点对点消息。普通主入口和非 Team 成员不可见这些协作工具。

标记为需要审批的成员在执行写入性工作前，必须先以约定的计划消息向 Lead 提交计划；只有收到 Lead 以约定结构明确批准的回复后才可开始实施。驳回或未获批准时，成员不得开始该实施工作。

### F4：邮箱与结构化消息协议

消息使用“成员名称注册表定位 + 收件人邮箱落盘”的两段式传递。每条消息包含发件人、正文、时间戳、已读状态和摘要；写入时自动补充时间戳、默认未读。每名成员拥有按其稳定身份隔离的邮箱文件；写入和读取必须在并发下保持完整，短暂拿不到锁时重试，过期锁可安全接管。

消息支持单播、广播，以及普通文本、关闭、计划审批、工作提醒和任务状态变化等结构化类型。使用独立终端后端时，消息送达还应唤醒目标终端，使空闲成员可继续处理消息；进程内成员通过相应的本地唤醒机制接收消息。

### F5：成员生命周期、空闲与续写

Lead 可派生成员、查看成员状态、停止成员和删除团队。成员完成当前工作后自然进入空闲状态，并将结果或状态变化通知 Lead。成员的会话记录持久化到磁盘；Lead 随后向已停止或空闲成员发送消息时，系统应恢复该成员的上下文并继续任务，而不是新建一个无上下文成员。

团队删除或成员停止时，应清理其可安全移除的运行资源；存在未收敛变更、运行异常或无法安全判断的资源必须保留并向 Lead 报告，不能静默丢弃。

### F6：Lead 的收敛与 Git 合并

Lead 可将用户目标拆成带依赖的共享任务、分配给成员，并在成员完成后收敛各可写成员的 Git 变更。收敛时，系统依次尝试合并已完成成员的变更；可自动解决的冲突可继续合并。发生无法安全自动解决的冲突时，必须撤回本次未完成的合并并向 Lead 报告冲突成员、已完成情况和需要人工决策的原因。收敛结果应清楚说明每个成员的合并、跳过、保留或失败状态。

### F7：Team 顶层入口与交互反馈

Lead 可通过顶层团队能力创建和删除团队，并可通过交互命令列出团队、查看团队或成员信息、删除团队及停止成员。创建、派生、消息送达、审批、成员空闲、恢复、收敛、清理和失败均应提供中文且可操作的反馈；团队中的 Lead 需要能在空闲时自动看到新的成员消息或状态提醒，无须用户额外输入。

### F8：Coordinator Mode 双锁与工作流

Coordinator Mode 只有在项目配置已开启该能力、且用户明确设置环境变量启用时才生效；任一条件不满足时保持普通 Lead 行为，并能说明未启用原因。启用后，Lead 的工具集收窄为读类能力、Shell、团队派生与管理、消息、终止和代码收敛等编排能力；Lead 不可直接使用写文件能力。Shell 保留给 Git 检查、合并及必要的协调操作。

启用时应向 Lead 注入明确的四阶段工作流提示：Research、Synthesis、Implementation、Verification，使其先调研和拆解、再形成方案、委派实现、最后验证和收敛。该模式不得移除成员完成被委派工作所需的正常写入能力。

## 非功能需求

- N1：团队、成员、邮箱、会话记录、Worktree 和运行资源均须按项目、团队和成员身份隔离；团队数据不得写入其他项目、用户级团队目录或旧 MewCode 品牌目录。不可信名称、持久化数据和消息字段不得导致跨团队访问、路径逃逸或执行非预期命令。
- N2：成员、邮箱和任务的持久化更新应具备并发安全与崩溃后的可恢复性；损坏、过期或不安全的状态必须被安全拒绝并给出中文原因。
- N3：后端检测、后端选择、邮箱并发、任务依赖、审批、成员恢复、合并回滚、Coordinator 双锁与工具限制均须有不依赖真实模型服务的自动化测试。
- N4：所有用户可见的团队提示、错误和状态使用中文；新增能力不得破坏现有普通子 Agent、后台任务、Worktree、权限确认或项目目录边界。
- N5：开发完成后必须在 tmux 中启动 YuCode，进行真实对话请求的端到端验证，并逐项记录验收结果。

## 不做的事

- 不支持跨机器、跨主机或跨项目的分布式 Agent Team。
- 不提供队员之间的实时流式通信；消息以持久化邮箱为准。
- 不实现超出“依赖满足后可执行”的复杂任务图约束、资源调度、优先级优化或自动重排。
- 不承诺在未安装 tmux、未运行于 macOS iTerm2 且进程内后端不适用的环境中自动提供替代后端。
- 不让 Coordinator Mode 绕过既有权限、审批或 Git 安全保护。

## 验收标准

- AC1（F1）：请求创建团队 `demo` 和未声明写权限的成员 `alice`，验证团队以 `demo` 原名出现在当前项目中以 YuCode 品牌命名的本地状态目录，且旧 MewCode 品牌目录没有本次数据；`alice` 使用主工作目录且没有 Git Worktree。重启后查询，验证团队、负责人、成员身份、角色、审批标记、后端和状态仍可用。再创建明确可写的成员，验证其使用独立 Git Worktree，且不同项目、不同团队互不读取对方的持久化数据。
- AC2（F2）：分别在具备 tmux、具备 iTerm2、仅允许进程内运行以及没有可用后端的受控环境中创建成员，验证选择结果符合优先级且展示实际选择原因；明确指定不可用后端时验证操作被中文拒绝且未启动成员；自动选择失败时验证没有暗中换用其他后端。
- AC3（F3）：以 Team 成员创建多个带依赖任务并完成前置任务，验证后续任务仅在全部依赖完成后变为可执行；验证 Team 成员可见并使用协作工具，而普通主入口和非 Team 子 Agent 不可见。对需要审批的成员，验证未批准或驳回时无法开始写入工作，收到格式正确的批准消息后才可实施。
- AC4（F4）：向单个成员和全体成员发送文本及结构化消息，验证目标邮箱出现完整的发件人、正文、时间戳、未读状态和摘要，读取后状态正确更新；并发写入时验证邮箱没有丢失或截断消息，过期锁可恢复；独立终端目标收到消息后被唤醒。
- AC5（F5）：让成员完成后进入空闲或停止状态，验证 Lead 收到状态通知；随后给该成员发新任务，验证系统从其磁盘会话续写并保留此前上下文。停止或删除时，验证安全资源被清理，而有未收敛变更或检查失败的资源被保留并明确报告。
- AC6（F6）：分配两个可写成员在独立 Worktree 中完成可合并变更并收敛，验证主分支包含两人的结果且报告逐成员状态；制造可自动解决和不可自动解决的冲突，验证前者可继续，后者撤回未完成合并并报告人工处理原因，主分支不留下半完成状态。
- AC7（F7）：通过团队顶层入口创建和删除团队，并通过交互命令列出、查看、删除团队和停止成员，验证命令不被发送给模型且每项结果有中文反馈；成员在 Lead 空闲期间发来消息或完成通知时，验证 Lead 能自动看到提醒。
- AC8（F8）：分别只开启配置、只设置环境变量、同时开启和同时关闭时启动 Lead，验证仅双锁同时开启时进入 Coordinator Mode；在该模式下验证 Lead 看不到写文件能力但保留读类、Shell、团队、消息、终止和收敛能力，成员仍能执行获委派的写入工作；验证 Lead 收到四阶段工作流指导。
- AC9（整体）：在 tmux 中启动 YuCode，输入一个真实的多文件开发请求，创建团队、派生至少两名成员、分配依赖任务、交换消息并收敛变更；验证最终回复、Git 状态和成员通知符合预期，并对照本章 checklist 逐项记录结果。
