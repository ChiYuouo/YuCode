# 后台任务可见性与执行一致性 Spec

## 背景

2026-09-13 的三轮缺陷修复暴露出一类共同问题：后台执行体（fork Skill、定义式子 Agent、Team 成员）在运行期间对用户和 Lead 几乎不可见，且部分执行路径的提示词或机制与实际能力不一致。已修复权限确认死锁与 fork 委派套娃，但排查确认还存在四项同族缺陷：

1. `run_fork` 的 `progress` 参数被接收但从未使用，`show_skill_progress`、`ForkActivity`、`show_skill_summary` 这套进度 UI 在 fork 路径上永远不会触发；后台任务从启动到结束之间零反馈，用户无法区分"正在工作"与"已卡死"。
2. Team 成员运行在 `TeamService._running` 的独立协程中，不经过 `TaskManager`：`execution_timeout_seconds` 不覆盖成员（可无限运行）、Hook 的任务事件（TASK_START/STOP/COMPLETE）不覆盖成员、统一任务视图也看不到成员。
3. inline Skill 斜杠命令注入"请严格执行已激活 Skill"的用户消息，但 SOP 实际要到下一轮才进入系统提示；真实会话中模型曾回复"Skill 尚未激活"，属于提示词与机制不一致（与 fork 委派缺陷同类）。
4. 后台任务的权限确认卡在应答后永远停留在"已选择：正在继续…"：工具结果不回流 TUI，卡片永不收尾。

本章统一解决"看得见"与"说得准"两类问题，使所有后台执行体可观察、可查询、可取消，并消除提示词与实际机制的错位。

## 目标

- 后台子 Agent 与 fork Skill 运行期间，界面持续显示阶段进度（当前轮次与最近工具调用）。
- 用户可通过统一命令查看所有后台任务（含 Team 成员）的状态、耗时与用量，并可取消仍在运行的任务。
- `execution_timeout_seconds` 与任务 Hook 事件覆盖 Team 成员；Team 成员的既有 Lead 通知流程保持不变。
- inline Skill 的 SOP 随命令消息直接下发，模型无须依赖"下一轮注入"即可执行。
- 后台任务的权限确认卡在工具出结果后原地收尾，显示最终成功或失败。

## 功能需求

后台子 Agent（定义式与 fork）运行期间，界面应持续展示可识别的进度信息，至少包括当前迭代轮次与最近一次工具调用结果摘要。前台子 Agent 的结果回传、权限确认与既有展示行为保持不变，其内部进度同样经由统一通道可见。进度展示复用现有 `ForkActivity` 组件与 `show_skill_progress` 入口，由 `RunToCompletion` 的执行事件经任务层转发到界面；进度更新不得进入模型上下文，也不得阻塞任务执行。进度链路中断（如界面刷新异常）不得影响任务本身的运行与结果回传。

### F2：统一任务命令 /tasks

系统已提供 `/tasks`（列出）与 `/task info|cancel <任务标识>`（详情/取消）命令，本章保持其行为并把统一任务视图中的全部任务（子 Agent 任务与 Team 成员任务）纳入其输出；已结束任务保留在列表中直至当前会话结束。命令不发送给模型，纯本地交互。

### F3：Team 成员纳入统一任务体系

进程内（in_process 后端）成员的运行必须登记进统一任务视图，使其出现在 `/tasks` 列表中并接受 `execution_timeout_seconds` 约束；超时行为与子 Agent 一致（取消运行、状态标记为 TIMED_OUT、向 Lead 报告失败）。任务 Hook 事件（TASK_START、TASK_STOP、TASK_COMPLETE）对成员运行同样触发。tmux/iTerm2 独立进程后端的成员运行在另一进程中，不纳入本章超时与进度范围（不做跨进程任务管理）。成员现有的通知回流（成员完成/失败摘要进入 Lead 上下文）必须保持不变；成员的审批流程、邮箱协作、Lead 主动停止（TeamStop → STOPPED）与 Worktree 收敛行为不得改变。

### F4：inline Skill 的 SOP 随消息下发

inline 模式斜杠命令在注入用户消息时，应将 `rendered_sop`（参数已替换）直接附在消息中，并明确说明用户参数，模型不再依赖"下一轮系统提示注入"来获取指令。消息须声明该 Skill 已由命令装载，避免模型自行重复调用 LoadSkill 或误判"尚未激活"。fork 模式的委派提示保持现有行为（已随任务下发 SOP）。

### F5：后台权限确认卡的结果收尾

后台任务的权限确认卡在对应工具调用出结果后，应原地更新为最终状态（成功或失败、含结果摘要），与前台权限卡行为一致；确认卡状态不得残留"正在继续…"。结果回流不得要求将子 Agent 的完整事件流接入主会话。

## 非功能需求

- N1：进度与通知只作为展示层信息，任何展示层异常不得影响任务执行、结果回传或主会话状态。
- N2：`/tasks` 与进度展示不得向模型上下文注入额外内容；任务标识、状态等持久化数据按不可信输入处理。
- N3：取消 Team 成员任务时，其运行资源清理与状态标记必须遵循 ch18 的成员生命周期规则，不得产生半完成的 Worktree 提交或邮箱悬空状态。
- N4：进度转发、任务命令、SOP 下发、权限卡收尾均须有不依赖真实模型服务的自动化测试。
- N5：所有新增用户可见文本使用中文；不得破坏现有权限确认多槽位行为、fork 委派提示与普通子 Agent 流程。
- N6：开发完成后必须在 tmux 中启动 YuCode 进行真实对话端到端验证，并对照 checklist 逐项记录。

## 不做的事

- 不做子 Agent 完整对话的实时流式展示；进度只到"轮次 + 最近工具"粒度。
- 不做跨会话、跨进程的任务持久化；`/tasks` 只覆盖当前会话内的任务。
- 不改变 Team 成员的审批、邮箱、Worktree 收敛协议。
- 不为 Team 成员新增独立的后端选择或进程模型。
- 不让进度展示或任务命令绕过既有权限确认与硬边界。

## 验收标准

- AC1（F1）：后台运行一个 fork Skill 与一个定义式子 Agent，验证界面在其运行期间持续出现轮次与最近工具的进度更新，任务结束后进度区收尾；制造一次界面刷新异常（模拟 progress 回调抛错），验证任务仍正常完成并回传结果。
- AC2（F2）：启动至少两个后台任务后执行 `/tasks`，验证列表包含全部任务及状态与用量；`/tasks <id>` 显示详情；`/tasks cancel <id>` 停止运行中任务并得到中文确认，被取消任务状态为 CANCELLED；对已结束任务执行取消得到明确的中文拒绝。
- AC3（F3）：创建团队并派生一名成员执行任务，验证 `/tasks` 列表中出现该成员任务；将 `execution_timeout_seconds` 设为极小值后派生成员，验证成员被超时停止、状态为 TIMED_OUT 且 Lead 收到失败报告；验证成员完成后 Lead 的通知回流与 ch18 行为一致，任务 Hook 事件按序触发。
- AC4（F4）：对 inline Skill 执行 `/skill:<名称>`，验证注入的用户消息包含完整 SOP 正文与用户参数；验证模型不再回复"尚未激活"，也无须自行调用 LoadSkill。
- AC5（F5）：让后台子 Agent 触发权限确认并应答"仅本次允许"，验证工具出结果后卡片原地显示最终成功或失败摘要；拒绝路径同样收尾。
- AC6（整体）：在 tmux 中启动 YuCode，真实执行"后台 review Skill + 后台定义式子 Agent + Team 成员任务"的并行场景，全程通过进度与 `/tasks` 观察状态；验证最终结果通知、Lead 回流与 Git 状态符合预期，并对照本章 checklist 逐项记录。
