# 上下文管理 Spec

## 背景

YuCode 会把持续对话、Agent 回复和工具调用结果一同带入后续模型请求。长时间任务中，工具结果通常是 Token 的主要来源；当累积历史接近模型上下文窗口上限时，请求可能失败或无法继续工作。

本功能要在不依赖精确 tokenizer 的前提下，让 YuCode 能主动控制历史大小：先外置过大的工具结果，再在必要时压缩较早历史，同时尽量保留用户提出的原始要求与近期工作细节。

## 目标

- 在默认 128K Token 上下文窗口内，让长会话持续可用；窗口大小可由用户配置，且对所有模型 Provider 使用同一上下文管理规则。自动压缩时为估算误差保留 13K Token 安全余量。
- 优先减少工具结果占用，且让外置的原始结果能被后续 Agent 重新读取。
- 在整体压缩后保留可执行的任务上下文、关键约束、文件状态和下一步工作。
- 允许用户主动压缩；该场景采用更小的 3K Token 安全余量。

## 功能需求

- F1：每次发起模型请求前，系统必须先检查本轮历史中的工具结果大小。单个工具结果超过 50K 字符时，必须将其完整内容保存至项目内的会话缓存，只在对话中保留结果摘要、可识别的预览、缓存位置和重新读取提示；下次启动 YuCode 时必须清理上一会话留下的此类缓存。
- F2：同一条消息中的工具结果字符数合计超过 200K 时，系统必须按结果大小从大到小依次外置，直到该消息的工具结果合计不再超过阈值；未被外置的结果保持原样。
- F3：外置工具结果后，Agent 必须能从保留的缓存位置重新读取其完整原文。外置不能改变工具调用成功或失败的语义，且外置记录必须足以识别原工具、调用目标、结果状态与原始内容的位置。
- F4：完成轻量外置后，系统必须评估整个待发送历史是否需要重量压缩。上下文窗口大小必须可配置，默认 128K Token，并对所有模型 Provider 通用。自动触发阈值为配置窗口减去 13K Token；用户输入 `/compact` 主动触发时，必须启动一次重量压缩，并以配置窗口减去 3K Token 为目标，不因当前估算低于自动阈值而忽略。若不存在可压缩的较早历史，允许以“无需压缩”结束。
- F5：重量压缩必须把较早历史替换为一份结构化摘要，保留从最新消息向前累计至少 10K Token 的近期原文，且无论其估算大小至少保留最近 5 条消息。较早用户消息应优先按原文保留，绝不修改其文字；只有为满足上下文硬限制而必须省略时，才允许不将其带入本次请求。
- F6：结构化摘要必须固定包含九个部分：原始用户要求（逐字引用必须保留的用户消息）、当前任务目标、已经完成的工作、已执行验证及其结果、当前代码与文件状态、重要决定与约束、最近读取的文件快照、当前可用工具与外置资料位置、未完成事项与推荐下一步。摘要只记录可由原历史支持的事实，不得补全、猜测或虚构代码细节。
- F7：生成摘要时，系统必须明确要求摘要模型不得调用工具；模型可以先产生仅供本次压缩使用的分析草稿，再产出正式结构化摘要。分析草稿不得写入对话历史、缓存或面向用户的界面。
- F8：每次重量压缩完成后，系统必须在历史中加入一条边界提示：摘要涉及的文件或工具结果需要细节时，应重新读取其原始文件或缓存，不得据摘要臆测代码或内容。
- F9：系统必须以最近一次模型 API 返回的输入 Token 用量为估算锚点；锚点之后新增内容只按字符量做近似估算。没有可用锚点时，系统也必须使用同一近似规则继续判断，不得因无法精确计数而跳过压缩保护。
- F10：系统必须提供 `/compact` 作为用户可见的手动压缩入口，并在压缩开始、成功、跳过和失败时给出清晰的中文状态。
- F11：当模型请求因 `prompt_too_long` 或等价的上下文超限错误失败时，系统必须立即执行一次紧急重量压缩，并使用压缩后的历史自动重试原请求一次；重试仍失败时，必须将明确的失败原因反馈给用户，不得无限重试。
- F12：自动摘要连续失败 3 次后，系统必须停止本会话后续自动摘要并明确提示已进入自动压缩熔断状态。手动 `/compact` 不计入该失败次数，也不受该熔断限制。

## 非功能需求

- N1：轻量外置与重量压缩必须在每次模型请求前按“先轻量、后重量”的顺序执行；任一阶段都不得改变用户已经输入的原始文本。
- N2：上下文管理不能阻塞工具执行结果的正常记录，也不能破坏既有工具调用、权限确认、普通对话与流式回复语义。
- N3：所有用户可见的状态、错误和熔断提示必须使用准确、易理解的中文，并明确区分自动压缩与用户手动压缩。
- N4：本阶段不引入精确 tokenizer、摘要策略的学习或自动优化；工具结果是否外置按字符数判断，整体历史长度以 API usage 锚点和字符近似估算，估算误差由既定安全余量承担。

## 不做的事

- 不修改、润色或重写用户原始消息来缩短上下文。
- 不将工具结果永久归档，也不承诺跨 YuCode 会话保留外置缓存。
- 不保证摘要可替代原始代码、命令输出或文件内容；需要细节时必须重新读取原始资料。
- 不为不同模型或任务自动学习、调整压缩阈值、摘要长度或保留策略。
- 不在本阶段实现精确 Token 计数器。

## 验收标准

- AC1（F1、F3）：构造超过 50K 字符的单个工具结果后发起下一次模型请求。观察到完整结果保存到项目内的本会话缓存，对话只保留可识别预览、位置和重新读取提示；按该位置重新读取可得到原始完整内容。重启 YuCode 后，上一会话缓存已被清理。
- AC2（F2）：构造一条消息内多个工具结果总计超过 200K 字符、但每项均未超过 50K 字符的场景。观察到系统从最大结果开始逐项外置，直到剩余合计不超过 200K 字符，较小且未被选中的结果仍保留原文。
- AC3（F4、F9）：以一次 API 返回的输入 Token 用量为锚点累积后续内容，使待发送历史估算达到配置窗口减 13K Token。观察到系统在请求前自动执行重量压缩；在没有锚点的会话中也能以字符近似值触发同类保护。用户输入 `/compact` 后，观察到系统执行一次压缩，并以配置窗口减 3K Token 为目标；修改窗口配置后，对不同 Provider 的触发计算均使用新的窗口值。
- AC4（F5）：准备包含多轮用户、Agent 与工具消息的长历史并触发重量压缩。观察到从末尾至少保留 10K Token 的原始消息；即使该范围较小，最近 5 条消息仍保留原文；较早用户消息优先以一字不改的形式保留。
- AC5（F6、F7）：触发摘要并检查送入后续请求的历史。观察到正式摘要完整覆盖九个固定部分、原始用户要求未被改写、没有未经历史支持的事实，且生成摘要期间没有工具调用；分析草稿没有出现在对话、缓存或界面中。
- AC6（F8）：重量压缩完成后让 Agent 需要摘要中涉及的代码或工具输出细节。观察到历史含有要求重新读取的边界提示，且 Agent 通过原始文件或缓存获取细节，而不是将摘要当作代码原文。
- AC7（F10、F12、N3）：用户输入 `/compact`，分别模拟成功、无需进一步缩短与失败。观察到中文状态清晰说明结果及手动触发方式；连续模拟 3 次自动摘要失败后，观察到自动熔断提示且本会话不再自动摘要，但后续 `/compact` 仍可发起摘要且不会增加自动失败计数。
- AC8（F11）：模拟模型返回 `prompt_too_long`。观察到系统紧急压缩后仅自动重试原请求一次；若重试仍返回上下文超限，观察到清晰的中文失败提示且没有第三次请求。
- AC9（N1、N2、N4）：在含大工具结果且总体历史接近阈值的对话中继续正常使用工具并接收流式回复。观察到每次请求前先执行轻量外置、再判断重量压缩；工具成功/失败语义、权限确认和普通对话保持正常，且未使用精确 tokenizer 或自动阈值学习。
