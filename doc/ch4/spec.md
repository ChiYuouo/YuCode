# YuCode 结构化系统提示与缓存策略 Spec

## 背景

YuCode 目前只向模型传入简短的模式指令，尚未统一表达助手身份、行为约束、工具规则、安全边界和输出风格等稳定要求。随着 Agent 可以多轮调用工具，缺少稳定、分层的指令会降低模型对“先读后改”“优先使用专用工具”等约定的遵守率。

同时，重复发送相同的全局指令和工具定义会增加延迟和费用。需要将稳定内容放在可被模型服务缓存的请求部分，将随运行变化的环境和模式信息独立注入，并用可观测数据验证缓存策略实际生效。

## 目标

- 建立一套按优先级组合的结构化系统提示，使 YuCode 在不同任务中具有一致的角色、行为和安全边界。
- 让稳定指令与工具描述能够复用模型服务的提示缓存，减少重复处理的时间和成本。
- 让环境信息和运行期补充规则能在不污染稳定缓存、不被误认为用户请求的前提下传递给模型。
- 让会话级任务模式在多轮 Agent 运行中保持有效，同时控制重复注入频率。
- 通过缓存命中数据和典型人工场景，验证策略的有效性与质量。

## 功能需求

- F1：系统提示由七个固定职责模块组成，并按以下优先级顺序拼接：身份、系统约束、任务模式、动作执行、工具使用、语气风格、文本输出；固定模块之间以空行分隔，环境信息始终位于其后。
- F2：系统应支持在固定模块之后追加可选模块，顺序固定为：自定义指令、已激活的 Skill、长期记忆。未提供的可选内容不产生空白占位；本章不要求实现这些内容的加载或存储能力。
- F3：系统应区分稳定内容与动态内容。稳定的全局指令和当轮可用工具描述以适合服务端提示缓存复用的方式发送；环境信息、对话历史和运行期补充规则不与稳定内容混合，并通过消息通道发送。
- F4：系统在全局指令与每项相关工具描述中双重表达关键操作规则，至少覆盖“优先使用适用的专用工具”和“编辑已有内容前先读取相关内容”。规则应不与既有只读规划模式、安全边界或工具能力相冲突。
- F5：系统可在运行中使用 `<system-reminder>` 与 `</system-reminder>` 包裹补充指令。模型应将其视为系统级补充约束，而非用户消息，不应直接针对标签或其内容向用户作答；该补充内容不应改变稳定提示的缓存身份。
- F6：每轮请求都应包含与当前运行相关的环境信息，例如当前工作范围及其他已有运行上下文；环境变化后，后续请求应反映新值，而无需重建稳定系统提示。
- F7：会话级开关的指令（包括规划模式）按轮次注入：第 1 轮使用完整版本；第 5、10、15……轮再次使用完整版本；其余轮使用保持同一约束含义的精简版本。完整和精简版本均不得允许该模式禁止的行为。
- F8：系统应从模型 API 响应中读取并累计可用的提示缓存用量或命中字段，并以可供界面或日志消费的方式提供本次请求的缓存观测结果。供应商未返回此类字段时，应明确显示为不可用，而不能伪报命中或未命中。
- F9：为本章提供一组可重复执行的典型人工对比场景，至少覆盖：普通的读取后编辑任务、规划模式的只读探索任务、含环境变化的多轮任务，以及能观察缓存复用的重复任务。每个场景应说明输入、观察重点和预期行为。
- F10：系统约束必须以明确优先级表达硬性工具流程：能使用适用专用工具时不得以通用命令替代；修改已有文件前必须先读取目标及相关上下文；写入或编辑成功后，若任务包含可验证结果，必须使用适用的只读工具或命令验证实际结果；任一前置条件不满足时不得伪造后续成功。
- F11：系统必须区分用户的任务授权边界。用户明确要求执行、修改、创建或验证时，助手应在既有安全限制内完成闭环；用户仅提问、要求解释、评审或建议时，不得自行修改文件、执行命令或扩大任务。用户意图不足以安全决定副作用时，可先使用只读工具理解上下文，仍无法判断时应向用户说明所需选择。
- F12：系统必须以硬性事实与安全规则约束模型：不得猜测未读取的内容、声称未执行的工具结果、掩盖失败或把计划表述为已完成；不得在最终回复中泄露密钥、令牌、密码、Cookie 或其他敏感内容。工具结果不足、冲突或失败时，应如实说明事实、影响和下一步。

## 非功能需求

- N1：相同的系统提示职责、模式约束和缓存观测语义在当前支持的模型供应商之间保持一致；供应商协议差异不应改变用户可观察的行为。
- N2：稳定内容在内容及工具集合未变时保持确定性；相同输入产生的模块顺序、空行分隔和文本内容一致，以利于缓存复用与测试。
- N3：动态环境信息、补充规则和会话历史不得被写入长期配置、稳定提示模板或跨会话缓存标识中。
- N4：新增提示与缓存策略不得破坏既有流式回复、Agent 多轮工具调用、命令确认、工作目录安全边界、`/plan` 只读限制及 Token 用量展示。
- N5：缓存观测与人工对比评估不应要求真实 MCP 接入，也不应依赖项目指令文件、自动记忆或自动化评估系统。
- N6：硬性规则的措辞应采用清晰的“必须/不得/仅当”条件，并集中于稳定提示前缀；同一规则不得在不同模块或工具描述中出现相互矛盾的例外。

## 不做的事

- 不加载、解析或合并项目指令文件。
- 不实现自动记忆、长期记忆的存储、检索或写入；长期记忆只预留为可选提示模块的位置。
- 不接入真实 MCP 服务或新增远程工具协议。
- 不建立自动化模型质量评估、基准评分或线上 A/B 实验。
- 不新增用户可配置的提示编辑界面或持久化的自定义指令管理。
- 不改变既有工具的实际权限、确认策略或工作目录访问范围。

## 验收标准

- AC1（F1、N2）：构造完整输入后，观察到的系统提示严格按七个固定模块的既定顺序输出，模块间恰有空行，环境信息位于固定模块之后；重复构造相同输入得到完全相同的稳定部分。
- AC2（F2）：分别在没有、只有部分和同时具有全部可选内容时，观察到可选模块仅追加在环境信息之后，顺序为自定义指令、已激活的 Skill、长期记忆，且不存在空白占位。
- AC3（F3、N3）：连续两轮使用相同全局规则和工具、但环境或历史不同的请求中，稳定部分保持不变；环境、历史和补充规则作为独立消息出现，未混入稳定部分。
- AC4（F4）：在“修改已有文件”和“存在适用专用工具”的代表性任务中，发送给模型的全局规则和对应工具说明均可观察到相关约定；在真实端到端对话中，模型先读取相关内容再修改，并优先调用适用专用工具。
- AC5（F5）：含 `<system-reminder>` 的运行期补充规则在后续模型行为中生效；模型不会把标签内容当作用户问题直接回答，也不会在用户可见回复中无关地复述该标签。
- AC6（F6）：同一 Agent 运行中环境信息发生变化后，下一轮模型请求携带更新后的环境信息，同时稳定系统提示保持不变。
- AC7（F7）：运行至少 11 轮的规划模式任务时，第 1、5、10 轮携带完整模式约束，其余轮携带精简约束；所有轮次仅可使用读取、查找和搜索等既有只读能力，且最终回复保持规划而非执行。
- AC8（F8）：对于返回缓存字段的模型请求，界面或日志可观察到本次请求的缓存相关用量；在稳定内容与工具不变的重复请求中，能够据返回字段判断是否发生缓存复用。供应商未提供字段时，结果明确标为不可用。
- AC9（F9）：按定义的四类人工对比场景分别运行后，记录每个场景的输入、工具调用顺序、最终回复和缓存观测；结果满足先读后改、规划只读、环境更新生效和重复请求可验证缓存策略的预期。
- AC10（N1、N4、N5）：在当前两个模型供应商上各完成一次“读取项目信息 → 修改文件 → 验证结果 → 最终回复”的端到端任务，以及一次 `/plan` 只读任务；既有 Agent、流式显示、确认和安全边界均正常工作，且整个过程不依赖项目指令文件、自动记忆、真实 MCP 或自动化评估。
- AC11（F10）：捕获“修改已有文件”和“验证修改结果”两类模型请求时，全局提示与相关工具描述均可观察到不可跳过的先读、专用工具优先与验证规则；在模拟模型先请求编辑、再请求验证的流程中，未读取前的编辑请求被阻止或纠正，验证失败不会产生“已完成”的最终回复。
- AC12（F11）：对“解释代码作用”“评审一段代码”“创建并验证文件”和“需求不完整但可能产生副作用”四类输入分别运行；前两类不发生副作用，第三类在既有安全边界内完成闭环，第四类最多使用只读工具且在无法安全判断时明确请求用户选择。
- AC13（F12、N6）：模拟未读取即回答、工具失败、验证失败、计划模式和包含模拟敏感值的工具输出；最终可见回复不捏造事实、不把计划当实施、不隐藏失败、不回显敏感值，且稳定提示中的对应规则均使用无冲突的强制条件表述。
