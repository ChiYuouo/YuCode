# MewCode 权限模式边界与内嵌确认 Spec

## 背景

第五章已引入四档权限模式和人工确认，但当前存在三类可观察问题。第一，旧的任务授权判断会先于权限模式拒绝某些明确的中文写入请求，例如“写一个数字 1 到 hello.txt”，使 `acceptEdits` 看似生效、实际仍以只读理由拒绝。第二，人工确认以独立页面呈现，打断对话上下文，和终端编程助手在对话流内暂停并等待确认的体验不一致。第三，任务授权、工具流程和权限模式分别产生拒绝结果，用户难以判断一次失败究竟属于权限不足，还是尚未满足“先读后改”等操作前置条件。

本章统一四档权限状态与既有 Do/Plan 入口的边界，确保用户在 `acceptEdits` 下提出明确文件写入或编辑请求时可以执行；同时将需要确认的操作改为聊天记录内的待确认卡片，以键盘完成选择。

## 目标

- 消除四档权限状态与 Do/Plan 入口的重叠和互相覆盖，使当前状态及其工具范围可预测。
- 让常见且明确的中文执行请求正确进入执行路径，不再被脆弱的关键词遗漏误判为只读。
- 将人工确认融入对话流，使用户在不离开当前聊天上下文的情况下决定是否执行操作。
- 让每次工具调用只经过一条权威裁决链，并清楚区分安全拒绝、权限决定与可修复的工具流程前置条件。
- 保持危险命令黑名单、路径沙箱、明确拒绝规则和拒绝后 Agent 可调整策略的既有安全边界。

## 功能需求

- F1：系统必须只使用以下四种会话级权限状态：`default`、`acceptEdits`、`plan`、`bypassPermissions`。`default`、`acceptEdits` 与 `bypassPermissions` 均属于 Do 执行状态；`plan` 是唯一的只读规划状态。Do 不是第五种权限状态。
- F2：`default` 下，未命中的有副作用调用必须请求人工确认；`acceptEdits` 下，未命中的项目内专用文件创建、写入和编辑必须直接执行，未命中的命令仍必须请求确认；`plan` 下只能使用只读工具；`bypassPermissions` 下未命中的有副作用调用无需确认。四种状态都不得绕过危险操作黑名单、专用文件工具路径沙箱或明确匹配的 `deny` 规则。
- F3：用户通过 `/plan` 或选择 Plan 时，系统必须切换到 `plan`；通过 `/do` 离开 Plan 时，必须恢复进入 Plan 前最后使用的 Do 权限状态。首次没有历史 Do 状态时，`/do` 恢复为 `default`。`Shift+Tab` 必须在四种状态间循环，并让状态区域立即显示实际生效状态。
- F4：系统必须识别常见、直接表达执行意图的中文请求，包括“写”“写入”“创建”“新建”“修改”“编辑”“删除”“运行”“执行”等；这类请求在 Do 状态不得因关键词遗漏被误判为只读。单纯解释、评审、建议、比较或提问仍不得因模型自行调用工具而产生副作用。
- F5：当当前状态要求人工确认时，系统必须在聊天记录内、紧邻对应工具请求显示待确认卡片，而不得打开独立页面或遮挡整个对话。卡片必须显示脱敏后的工具、目标和影响说明，并明确表示操作尚未执行。
- F6：内嵌待确认卡片必须提供四个选择：仅本次允许、本会话允许、永久允许、拒绝。用户必须可使用数字 `1` 到 `4` 直接选择，也可用上下方向键和 Enter 选择；Escape、取消生成或失去有效确认状态时等同于拒绝。四种选择的权限范围继续遵守第五章定义。
- F7：待确认期间，真实工具必须保持未执行，当前 Agent 任务处于可观察的等待状态；确认后卡片应原地更新为选择及结果，随后恢复工具执行或将结构化拒绝结果回传给模型。确认或拒绝不得丢失已有对话、工具活动或滚动位置。
- F8：明确拒绝、黑名单拒绝、路径拒绝和规则拒绝都必须继续以结构化结果回传模型，Agent Loop 仍有机会在后续轮次改用安全调用、只读调用或向用户解释所需授权。
- F9：每次工具调用必须由同一条权威裁决链给出唯一结果，不得由互不知情的权限判断先后覆盖。裁决顺序固定为：不可绕过的危险边界、路径边界、本次用户执行意图、明确拒绝规则、工具流程前置条件、只读调用、明确允许规则、权限模式回退与人工确认。
- F10：任务执行意图和“编辑或覆盖前先读取、写入后再验证”等流程要求不得表现为额外权限模式。未满足流程要求时，结果必须明确标识为可修复的流程前置条件，并允许 Agent 先补足读取或验证后重试；`acceptEdits` 和明确 allow 规则均不得跳过这些流程要求。

## 非功能需求

- N1：权限状态、工具可用范围、状态区域文字与实际执行决定必须保持一致；同一状态和调用得到确定性结果。
- N2：内嵌确认卡片的键盘焦点必须清晰，不应把选择数字、方向键、Enter 或 Escape 误写入普通消息输入框。
- N3：卡片中的命令、路径与影响说明必须沿用敏感信息脱敏；不得显示完整文件写入内容或凭据。
- N4：从等待确认到选择、取消或 Agent 完成的状态变化不得遗留不可完成的等待任务，也不得让输入框永久禁用。
- N5：每次拒绝或等待确认必须只有一个主原因和稳定分类，界面与模型历史看到的分类必须一致，不得同时出现相互矛盾的“权限允许”和“策略拒绝”。

## 不做的事

- 不新增第五种“Do”权限模式，也不再维护与权限状态独立的 Do/Plan 状态来源。
- 不修改危险命令黑名单、路径沙箱、规则 YAML 格式、规则优先级或永久规则的保存位置。
- 不新增鼠标专用的权限设置页、图形化规则编辑器、审计日志或网络权限控制。
- 不改变永久允许只能写入项目本地且被 Git 忽略的约束。
- 不取消“修改前先读、写入后验证”等既有流程保护；本次只统一其裁决入口和错误语义。

## 验收标准

- AC1（F1、F2、N1）：分别在四种状态发起未匹配文件写入、编辑、命令和只读调用；观察到 default 请求确认，acceptEdits 直接执行项目内文件操作但确认命令，plan 仅暴露只读工具，bypassPermissions 跳过未命中确认；黑名单、路径沙箱和 deny 在全部状态中仍拒绝。
- AC2（F3、N1）：从 acceptEdits 和 bypassPermissions 分别切换到 Plan，再执行 `/do`；观察到每次都恢复进入 Plan 前的对应 Do 状态。首次执行 `/do` 时观察到恢复 default；Shift+Tab 每次切换后状态区域和下一次工具调用的行为一致。
- AC3（F4）：输入“写一个数字 1 到 hello.txt”“创建一个文件”“修改已有文件”等直接请求；在 acceptEdits 下观察到文件调用不被“未明确授权副作用”拒绝。在解释、评审和提问场景中模拟模型写入调用，观察到不产生副作用。
- AC4（F5、N2、N3）：在 default 下触发需确认的文件操作和命令；观察到待确认卡片出现在聊天流中而非独立页面，展示脱敏工具/目标/影响，普通输入框不接收确认按键文本。
- AC5（F6、F7、N4）：分别用数字 1～4、方向键加 Enter、Escape 和取消生成操作待确认卡片；观察到四种授权范围正确、工具只在允许后执行、卡片原地更新、拒绝回传模型，且输入和会话恢复正常。
- AC6（F8）：让模型首次发起被拒绝的调用后改用项目内安全调用；观察到首次无真实副作用、模型收到结构化原因和下一步、Agent Loop 继续且替代调用完成。
- AC7（F9、F10、N5）：在 `acceptEdits` 下分别触发明确写入、缺少前置读取的覆盖、危险命令、路径逃逸和明确 deny；观察到每次只返回一个稳定分类。明确写入按模式执行，缺少读取返回可修复的流程前置条件且补读后可重试，后三类保持不可绕过拒绝；界面和模型历史中的原因一致。
